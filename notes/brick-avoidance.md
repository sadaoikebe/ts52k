# 文鎮化を避けるための運用ルールと手順

2026-11-11作成（ブランチ claude-fable-brickproof-2026-11-11）。実機は未検証。
根拠と経路の一覧は報告書 `~/workspace/bus-redesign-2026-11-10/fable-brickproof-report.md` にある。
ここには、守るルールと、初回書き込み・復旧の手順だけを書く。

## 前提：何が戻せて、何が戻せないか

- **ソフトウェアだけで戻せなくなる状態は、nRF52840にはない。** SWDのCTRL-APから全消去（recover）すれば、
  ブートローダ・ZMK・UICR（REGOUT0、リセットピン、APPROTECT）は全て初期状態に戻る。
  CTRL-APのレジスタはRESET／ERASEALL／ERASEALLSTATUS／APPROTECTSTATUS／IDRで、全消去を禁止するレジスタはない
  （pyOCDのnRF52実装で確認。Nordicの製品仕様書は今回取得できず、原典では未確認）。
- **戻せないのは物理的な破壊だけ。** 電池の逆接続、SWD端子への過電圧、静電気、部品の向き違い。
- したがって命綱は「J2のSWD接点」「USB給電」「1.8 Vに対応した書き込み器」の3つ。これを失う操作を避ける。

## 守るルール

### 電源・電池

1. **電池をつなぐ前に、必ずテスターで極性を確かめる。** J3は1番（シルクの「+」側）がBAT+、2番（「−」側）がGND。
   PHコネクタ付き電池の極性は製品ごとに逆のものがある。逆接続を防ぐ回路は基板にない。
   逆に挿すと充電IC（U6）とモジュール（U5）が壊れ、SWDでも戻せない。
2. **初回書き込みからUSB動作確認までは、電池をつながない。** USB給電だけで全工程ができる。
3. 保護回路付きの電池だけを使う。基板側に過放電の遮断はない。充電電流は最大約100 mAなので、小容量すぎる電池は使わない。
4. 最初の通電は、電流の見えるUSBテスターか、PCではないUSB電源を介す。モバイルバッテリーは使わない
   （消費電流が小さいと自動で給電を止める機種がある）。

### SWD（書き込み器）

5. **3.3 V固定の書き込み器を、VDDが1.8 Vの基板につながない。** 未書き込み・全消去直後のVDDは1.8 V。
   Raspberry Pi Debug Probe、ST-Link互換品、Picoの自作プローブなどは3.3 V固定で、端子の定格（VDD＋0.3 V）を超える。
6. **J2の1番（VTref）へ電源を供給しない。** ここはモジュールのVDD（REG0の出力）に直結している。書き込み器の3.3 V出力や5 V出力をつながない。
7. 書き込み器はJ-Linkを1台だけPCに挿す。開発キットなど他のJ-Linkが挿さっていると、別の基板を消去しうる。
8. Tag-Connectは向きを確かめてから当てる。位置決め穴は片側1個・反対側2個で、逆向きには入らない。

### 書き込む物

9. **`update-*.uf2`（ブートローダ更新用UF2）や、ブートローダを含むDFUパッケージを書かない。**
   nice!nano用の更新UF2はこの基板のブートローダが受け付けてしまう（USBのVID/PIDが同じため）。
   更新中の電源断や内容の不一致は、SWDでしか戻せない。やるなら書き込み器が手元にあるときだけ。
10. **他のキーボード用のUF2を書かない。** ピンの使い方が違う。エンコーダ（rpg1=P1.11、rpg2=P1.13）は接点が閉じるとGNDへつながるので、
    この2本を出力Highにするファームウェアでは端子が短絡状態になる。
11. ZMKは必ずアプリ開始0x26000・保存領域0xEC000〜0xF3FFFのレイアウトでビルドする（PC側チェックリスト参照）。
    保存領域が0xF4000以降にかかるビルドは、動作中にブートローダを消す。
12. ZMKのキーマップに `&bootloader` を必ず1か所入れる。SW1（リセット）は基板の裏面にあり、ケースを開けないと押せない。

### 組み立て

13. **1枚目で初回書き込み・USB・ZMK起動まで完走してから、スイッチのはんだ付けと2枚目に進む。**
14. スイッチとプレートを付けた後は、Tag-Connectの保持クリップは使えない（表面側に入らない）。手で押さえて使う。
15. SW1は裏面にあり高さ約1.5 mm。電池やケース底面が常時押す配置にしない（リセットがかかり続け、起動しないように見える）。

## 初回書き込みの手順（1枚ずつ）

書き込み器はJ-Link EDU Mini V2＋TC2030-CTX-NLを想定。コマンド名はnRF Utilの版で変わりうるので、
事前に `nrfutil device --help` で確かめる（Nordicの文書サイトは今回取得できず、下のコマンド名は未照合）。

### 0. 基板が届く前

- PCにJ-Link Software PackとnRF Util（`nrfutil install device`）を入れ、書き込み器単体が認識されることを確かめる。
- `nice_nano_bootloader-0.11.0_s140_6.1.1.hex` のSHA-256が
  `1b72d4cd163239dec96231b3549d541cbc96b7a64b3041b635482ca4d7441f7e` であることを確かめる。
- ZMKのUF2を新しい18本のピン割当てでビルドし、PC側チェックリストを済ませておく。

### 1. 通電前（電池なし、USBなし）

- 目視：U5（モジュール）とU6（充電IC）の1番ピンの向き、J1のはんだ、部品の欠け・ブリッジ。
- テスターで短絡がないこと：USB_VBUS–GND（C22）、VDDH–GND（C25）、nRF_VDD–GND（C27）、nRESET–GND（SW1を押していない状態で開放）。

### 2. USBだけで通電

- VDDH（C25）が約3.4〜4.4 V、nRF_VDD（J2の1番、またはC27）が**約1.8 V**（未書き込みの値）であること。
  0 Vなら電源系の不良。ここで止める。3.3 Vなら既にUICRが書かれている（それでも次のrecoverで初期化される）。
- 異常な発熱や、USBテスターで数十mAを超える電流があれば、すぐ抜く。

### 3. SWD接続と全消去

- J2にTag-Connectを当て、J-Link Commander（対象 `nRF52840_xxAA`、SWD、速度100 kHz）でVTrefが約1.8 Vと表示されることを見る。
- `nrfutil device recover` を実行する。保護の有無にかかわらず、最初に必ず行う（工場出荷時の内容とUICRを消し、状態をそろえる）。
- 接続できたら、チップの版を記録する：`mem32 0x10000100 2`（品番と版。2語目がASCIIで `AAF0` 以降なら保護強化版）。

### 4. 書き込みと照合（まだリセットしない）

- `nrfutil device program --firmware nice_nano_bootloader-0.11.0_s140_6.1.1.hex` を、照合（verify）付きで実行する。
- **リセットする前に**、J-Link Commanderで次を読む。
  - `mem32 0x10001014 2` → `000F4000 000FE000`（ブートローダの位置。これが無いとブートローダが起動しない）
  - `mem32 0x10001208 1` → 下位1バイトが `5A`（保護強化版で、次回以降もSWDを開けるための値）
- `0x10001208` が `FFFFFFFF` のままなら、リセット前に書く：
  `w4 0x4001E504 1` → `w4 0x10001208 0x0000005A` → `w4 0x4001E504 0` → `mem32 0x10001208 1` で確認。
  （書かなくても文鎮にはならない。次にSWDを使うとき全消去が必要になるだけ。）

### 5. リセットと確認（SWDではなくUSBで見る）

- リセットすると、ブートローダが自分でUICRを3か所書いて再起動を繰り返す（NFC端子、リセットピンP0.18、REGOUT0=3.3 V）。
- **確認はUSBとテスターで行う。** PCに `NICENANO` ドライブが現れ、`INFO_UF2.TXT` が読め、nRF_VDDが**約3.3 V**になっていること。
- **この時点でSWDがつながらなくても故障ではない。** 保護強化版のチップでは、ブートローダだけが動いている間SWDは閉じている
  （このブートローダは保護を開ける処理を持たない）。**ここでrecoverや、J-Linkの「解除しますか」に「はい」を選ぶと、書いたばかりのブートローダが消える。**

### 6. ZMKの導入

- `NICENANO` ドライブへTS52K用のZMK UF2をコピーする。再起動後、USBキーボードとして認識されることを確かめる。
- SW1を2回すばやく押して `NICENANO` ドライブへ戻れることを確かめる（以後の復旧手段の確認）。
- ZMKが動いている状態では、`0x10001208` が `5A` ならSWDで読み出し・デバッグができる（Zephyrの既定動作）。

### 7. そのあと

- 2枚目以降も同じ手順。スイッチのはんだ付け、電池の接続（極性確認のうえ）はこのあと。

## 動かなくなったとき

上から順に試す。下へ行くほど消えるものが増える。

| 症状 | 手段 | 消えるもの |
| --- | --- | --- |
| ZMKが固まる・キーが効かない | SW1を1回押す | なし |
| ZMKが起動しない・書き換えたい | SW1を0.5秒以内に2回押す→`NICENANO` ドライブ→正しいUF2をコピー | 旧ZMK |
| 設定やペアリングがおかしい | TS52K用の `settings_reset` UF2→通常のUF2 | ZMKの設定・ペアリング |
| `NICENANO` は出るがUF2を書いても起動しない | 0x26000開始でビルドしたUF2か確かめる。違うレイアウトのUF2を書いた後なら次の行へ | — |
| `NICENANO` ドライブが出ない | USBケーブル・ポートを替える→nRF_VDD（3.3 V）とVDDHを測る→SWDへ | — |
| 上のどれでも戻らない | SWD：recover→初回書き込み手順の4〜6 | 全て（ブートローダから入れ直し） |
| SWDがつながらない | 下の切り分け | — |

SWDがつながらないときの切り分け：

1. nRF_VDD（J2の1番）を測る。0 Vなら電源系（USB、U6、VDDH）。1.8 Vか3.3 Vなら次へ。
2. nRESET（J2の3番）がGNDへ落ちたままでないか（SW1の短絡、何かが押している）。
3. Tag-Connectの当たり（向き、押さえ、クリップ）。速度を100 kHzへ下げる。
4. 保護で閉じているだけなら `nrfutil device recover` は通る。通らないのは電源・配線・接触・書き込み器の側。
5. Tag-Connectが使えない場合、J2の接点（直径約0.79 mm、1.27 mmピッチ）へ細い線を直接はんだ付けしてつなぐ。
   1=VTref、2=SWDIO、3=nRESET、4=SWCLK、5=GND。

## PC側（zmk-config）のチェックリスト

このVMからは見えないので、PCで確認して `docs/ts52k-main-bringup.md` に結果を残す。

- [ ] ビルド後の `zephyr.dts`：`code_partition` が `0x26000` 開始、`storage_partition` が `0xec000`・長さ `0x8000`（終端0xF4000）。
- [ ] `.config`：`CONFIG_FLASH_LOAD_OFFSET=0x26000`、`CONFIG_BUILD_OUTPUT_UF2=y`、UF2のファミリーIDが `0xADA52840`。
- [ ] `.config`：`CONFIG_NRF_APPROTECT_LOCK` が `y` でないこと（既定は `CONFIG_NRF_APPROTECT_USE_UICR=y`）。
- [ ] `zephyr.dts` の `&uicr`：`gpio-as-nreset` あり（リセットピンP0.18。ブートローダの設定と同じ）。P0.18をkscanなど他の用途に割り当てていない。
- [ ] REG0・REG1のDC/DC有効の設定が入っている一方で、**両方LDOにした予備ビルドのUF2も作って保管する。**
      L1（REG0用10 µH）のはんだ不良などでDC/DCが動かない基板でも、ブートローダはLDOで動くので、予備ビルドへ書き換えれば切り分けられる。
- [ ] 同じく、LFクロックを内蔵RCにした予備ビルドを作る（32.768 kHz水晶が発振しない場合の切り分け用）。
- [ ] P0.13を外部電源制御（EXT_POWER）に使う設定が残っていない（基板ではrow3）。
- [ ] キーマップに `&bootloader`（と、できれば `&sys_reset`）がある。
- [ ] TS52K用の `settings_reset` UF2を作って保管する（nice!nano用の配布物を流用しない）。
- [ ] 初回HEXと、動作確認済みのZMK UF2・予備ビルドUF2を、ハッシュと一緒に1か所へ保管する。
